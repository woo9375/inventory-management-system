# Graph Engineering — 구조화된 작업 실행 방법론

## 개요

그래프 엔지니어링은 복잡한 작업을 **노드(역할 단위)**와 **엣지(의존성/흐름)**로 구조화하여, 단일 프롬프트의 한계(환각, 누락, 품질 편차)를 구조적으로 극복하는 방법론입니다.

> **적용 기준**: 아래 중 하나 이상에 해당하면 이 방법론을 적용하세요.
> - 3개 이상의 파일을 수정해야 하는 작업
> - 백엔드 + 프론트엔드를 동시에 변경해야 하는 작업
> - 기존 비즈니스 로직(FIFO, RBAC 등)에 영향을 줄 수 있는 작업
> - 마이그레이션이 필요한 구조 변경

---

## 핵심 패턴: 다이아몬드 (Diamond Pattern)

```
                    ┌──────────────────────┐
                    │  🧠 Node 1: 아키텍트  │
                    │  (분석 + 전략 설계)    │
                    └─────────┬────────────┘
                              │
                     ═══ 사용자 승인 ═══
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
     ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
     │ Node 2A     │ │ Node 2B     │ │ Node 2C     │
     │ (영역 A)    │ │ (영역 B)    │ │ (영역 C)    │
     └──────┬──────┘ └──────┬──────┘ └──────┬──────┘
            └───────────────┼───────────────┘
                            ▼
                    ┌──────────────────────┐
                    │  ✅ Node 3: 검증자    │
                    │  (제약 + 무결성)      │
                    └─────────┬────────────┘
                              │
                     (위반 시 Node 2로 회귀)
                              │
                              ▼
                    ┌──────────────────────┐
                    │  📦 Node 4: 종합자    │
                    │  (통합 + 마이그레이션) │
                    └──────────────────────┘
```

---

## 각 노드의 역할 정의

### Node 1: 아키텍트 (분석 + 설계)

**목적**: 작업의 전체 그림을 파악하고, 구현 전략을 설계합니다.

**수행 내용**:
1. 현재 코드 분석 및 영향 범위 파악
2. 해결 전략 수립 (우선순위: 알고리즘 개선 → 데이터 구조 변경 → 아키텍처 변경)
3. 변경 영향도 매트릭스 작성 (파일별 변경 유형, 범위, 위험도)
4. GAS 환경 제약과의 충돌 여부 검토

**산출물 형식**:
- 전략 요약 테이블
- 변경 영향도 매트릭스 테이블
- 위험 요소 및 대응 방안

**⏸️ 체크포인트**: Node 1 산출물을 출력한 후, **반드시 사용자 승인을 받고** Node 2로 진행합니다.
```
"Node 1 분석이 완료되었습니다. 검토 후 Node 2 구현 단계로 진행할까요?"
```

---

### Node 2A/2B/2C: 전문가 (병렬 구현)

**목적**: Node 1에서 승인된 전략을 영역별로 분할 구현합니다.

**영역 분할 기준** (작업 성격에 따라 유동적으로 조정):

| 분할 유형 | Node 2A | Node 2B | Node 2C |
|----------|---------|---------|---------|
| **기능 기반** | 백엔드 (.gs) | 프론트엔드 (.html) | 데이터/캐시 |
| **모듈 기반** | 핵심 엔진 | API 레이어 | UI 레이어 |
| **우선순위 기반** | 필수 변경 | 권장 변경 | 확장 포인트 |

**산출물 형식**: 각 영역별 **수정된 함수의 완전한 코드** (생략 없이 복사-붙여넣기 가능)

> **중요**: Node 2가 2개 영역만 필요하면 Node 2A/2B만 사용합니다. 무리하게 3개로 나누지 마세요.

---

### Node 3: 검증자 (통합 검증)

**목적**: Node 2의 모든 산출물이 프로젝트 제약을 준수하는지 검증합니다.

**필수 체크리스트**:

#### GAS 환경 제약 (`.agents/rules/01_gas-environment.md` 참조)
- [ ] `import`/`export`/`require` 미사용
- [ ] `onEdit`(Simple Trigger) 30초 내 완료
- [ ] 모든 함수 6분 실행 제한 준수
- [ ] CacheService 항목당 100KB / 전체 25MB 미초과
- [ ] PropertiesService 키/값 각각 9KB / 전체 500KB 미초과

#### 비즈니스 로직 무결성 (`.agents/rules/02_business-logic.md` 참조)
- [ ] FIFO 로트별 단가 유지 로직 미변경
- [ ] 입출고 9열 구조 (`TX_COLS = 9`) 유지
- [ ] 시즌 배수 보정 로직 무영향
- [ ] RBAC 3단계 권한 검증 유지

#### 코드 규약 (`.agents/rules/04_code-conventions.md` 참조)
- [ ] 시트명 `Config.gs` 상수 사용 (하드코딩 없음)
- [ ] 기존 함수 시그니처 변경 시 호출부 전체 업데이트
- [ ] `google.script.run.함수명()` 호환성 유지

#### 하위 호환성 & 안전성
- [ ] 기존 데이터 유실 없음
- [ ] 배포 후 즉시 동작 (또는 마이그레이션 절차 명시)
- [ ] 롤백 가능 여부

**위반 발견 시**: 해당 Node 2의 코드를 수정하여 재출력합니다.

---

### Node 4: 종합자 (통합 + 마이그레이션)

**목적**: 검증 통과된 모든 코드를 통합하고 최종 산출물을 정리합니다.

**산출물**:
1. **파일별 변경 요약표** (1줄 요약)
2. **완전한 소스 코드** (수정된 함수 전체, 생략 없음)
3. **마이그레이션 가이드** (해당되는 경우):
   - 사전 백업 항목
   - 코드 배포 순서
   - 배포 후 1회 실행 함수
   - 정상 동작 확인 방법
   - 롤백 절차
4. **변경 전후 비교** (성능 개선이면 Before/After 예측, 기능 추가면 동작 시나리오)

---

## 간소화 모드: 순차 체이닝

작업이 비교적 단순하지만 구조화가 필요한 경우 (파일 2~3개 수정), 다이아몬드 패턴 대신 **순차 체이닝**을 적용합니다:

```
Node 1 (분석) → Node 2 (구현, 분할 없이 단일) → Node 3 (검증) → Node 4 (종합)
```

이 경우에도 **Node 1 → 사용자 승인 → Node 2** 체크포인트는 유지합니다.

---

## 적용 예시

사용자가 아래처럼 요청하면 이 스킬이 활성화됩니다:

- "그래프 엔지니어링으로 성능 최적화해줘"
- "복잡한 작업이니 구조화해서 진행해줘"
- "다이아몬드 패턴으로 리팩토링 해줘"
- "Node 분할해서 작업해줘"

**첫 번째 행동**: 작업 범위를 파악하고, 다이아몬드 패턴 vs. 순차 체이닝 중 적합한 구조를 선택한 후 Node 1부터 시작합니다.

---

## 토큰 소진 시 대응

작업 중 토큰이 소진될 경우:
1. 현재까지 완료된 노드와 산출물을 요약합니다.
2. 미완료 노드의 시작 지점과 남은 작업을 명시합니다.
3. 사용자가 새 세션에서 "이어서 진행해줘"라고 하면 요약을 기반으로 작업을 재개합니다.
